Why doesn't my BACnet value change when I write to it?

Updated 3 October 2026

Short answer

You wrote the point, the device accepted it, and nothing moved. Re-read the point and look at what changed. If the Present Value did not change, something at a higher priority is holding the point: your write landed in its slot and is being outranked. If the value changed but the equipment did not, the point is overridden at the hardware, Out Of Service, or the machine itself has a problem. If the value changed and then snapped back, the controller's own program is rewriting it. The point screen in Easy BACnet shows which priority is in command, which tells you which of the three you have.

First, re-read the point

Easy BACnet re-reads the point after every write, so the value on screen is what the device reports, not what you sent. Compare it with what you wrote, and look at Commanded At. Then pick the case below.

Case 1 — the value did not change

A commandable point has sixteen priority slots and follows the highest-priority slot that holds a value (1 is highest). If slot 5 holds 72 and you write 68 at slot 8, the point stays at 72. Your write was accepted and stored; it is simply outranked. Commanded At shows the winning priority and its value.

Two things to check:

  • Which slot is winning, and whose is it? Priority 1 and 2 are life safety, 5 is critical equipment, 6 is minimum on/off. If one of those holds the point, the control system has a reason and you should leave it. Priority 8 is another operator or a tool like this one; a stuck 8 is usually an override someone forgot to release.
  • Did your write carry a priority? A WriteProperty with no priority lands at 16, the lowest, so anything else wins. Easy BACnet always sends one (8 by default); some other tools do not.

The right fix is usually to release the slot that should not be held (write NULL at that priority) so the point falls back to the program, rather than to write at a higher priority and pile one override on another. See how to release a BACnet override and BACnet priority and stuck overrides.

Case 2 — the value changed, the equipment did not

The controller accepted the command and shows your value, but the fan did not start or the valve did not move. The controller is no longer the problem:

  • The point is Overridden. The Overridden status flag means something local to the device, typically a hand/off/auto switch at the equipment, is forcing the output. Nothing written over the network will move it.
  • The point is Out Of Service. The object is disconnected from its hardware for testing, so Present_Value changes freely and drives nothing.
  • The machine has a fault. A tripped overload, a locked-out compressor, a failed actuator. The command is correct; the mechanical side is not.

Check the point's status flags (see status flags explained). Overridden and Out Of Service are a controls visit; a healthy point with a dead machine is an HVAC visit.

Case 3 — the value changed, then snapped back

The controller's own logic writes that point every program cycle at the same or a higher priority, so your value lasts a second. You cannot win that from outside, and on a live system you should not try. If you need to hold the point, the program has to be changed or the point released from its control, which is a job for the controls contractor.

If the write was refused instead

If the device answered with an error rather than accepting the write, that is a different problem: see what does BACnet Write Access Denied mean? Input points and read-only Value objects fall in that category.
