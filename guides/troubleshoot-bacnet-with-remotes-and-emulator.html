How can a custom remote or the device emulator help me troubleshoot a BACnet IP system?

Updated 21 November 2026

Short answer

Most BACnet service calls come down to one question: is the command leaving the BMS, reaching the controller, and moving the equipment? Easy BACnet gives you a tool for each half. A custom remote puts the command, its proof (status or feedback) and the setpoint on one screen, so you can watch the controller react while you stand at the unit. The Device Emulator stands in for the controller, so you can see exactly what the BMS sends: which points, what values, at what priority. Between them you can tell a programming problem from a network problem from a mechanical one.

Build a checkout remote

For a rooftop unit, air handler or fan coil, one remote with eight or so controls covers most calls. Put each command next to its proof, so a mismatch is obvious:

  • Fan command (Toggle, coloured red) beside Fan status (Indicator).
  • Occupied cooling setpoint (Setpoint) beside Zone temperature and Supply air temperature (Readouts).
  • Occupancy or Mode (Multi-state).
  • A Release control next to every control that writes.

Build it once per unit; it stays on the phone for the next visit and can be shared as an .ebremote file with the next tech. The free version keeps one remote; Easy BACnet Pro keeps as many as you like.

Reading the remote when something is wrong

Command on, status off

The controller took the command, so BACnet is fine. Look at the equipment: a hand/off/auto switch, a tripped overload, a VFD fault, a failed current switch. Check the point's Overridden and Out Of Service flags too; see why a value doesn't change when written.

“Sent … but it still reads …”

After each write the remote reads the point back. When the device accepted the write but the value didn't move, it tells you, which means a higher priority (another operator, a schedule, the BMS) or the controller's own program is holding the point. Find out which before you write at a higher priority: BACnet priority and stuck overrides.

Values grey out

The device stopped answering. If it comes back by itself, suspect the network (a duplicate IP or Device ID, a flapping switch port, a busy MS/TP trunk behind a router) before the controller: see why a device shows offline.

When you need to see what the BMS sends

If the remote proves the controller and equipment work when you command them, but the BMS still can't run the unit, the question moves to the head-end. Take the real controller off the network, start the Device Emulator with its Device ID, and let the BMS send its commands. Each write is listed with the point, value, data type, priority and sender. Common findings:

  • No writes at all. The point isn't mapped, the schedule isn't active, or the head-end is bound to an old IP address.
  • Writes to the wrong point. For example AV 12 instead of AV 21: a mapping error.
  • Writes at priority 16. The head-end sends no priority, so almost anything at the controller outranks it.
  • Refused writes. A setpoint sent as the wrong data type, or a write to an input. The emulator shows the reason a real controller would give.
  1. 1: a write to a read-only input, refused: “read-only input”.
  2. 2: a setpoint sent as the wrong data type, refused with the reason.
  3. 3: a write with no priority lands at 16. It was accepted, but the point still reads 70 because priority 8 holds it. This is the classic “the BMS sent it and nothing happened”.

The free version emulates one Device ID with up to three points; Easy BACnet Pro removes the limits. Step by step: how to check what a BMS writes.

Leave it as you found it. Release every point you commanded from the remote, stop the emulator, and put the real controller back on the network before you leave site.
